# 예약 동시성 제어 방식 성능 비교

## 1. 문제

동일한 스터디룸의 동일 시간대에 예약 요청이 동시에 들어오면, 두 요청이 모두 중복 검사를 통과해 중복 예약이 저장될 수 있다.

StudyOn은 이 문제를 막기 위해 비관적 락과 낙관적 락을 각각 구현하고, 같은 조건에서 예약 정확성과 HTTP 성능을 비교했다.

## 2. 공통 테스트 조건

| 항목 | 조건 |
| --- | --- |
| 대상 API | `POST /api/v1/reservations` |
| 테스트 도구 | k6 |
| 서버 | 로컬 Spring Boot (`localhost:8080`) |
| DB | PostgreSQL `studyon_test` |
| 시나리오 | 100 VU, 총 100회 요청 |
| 예약 조건 | 같은 스터디룸(ID 1), 같은 날짜의 10:00~11:00 |
| 예약자 정보 | VU 번호를 사용해 요청마다 다르게 생성 |
| 실행 횟수 | 락 방식별 3회 |
| 사전 정리 | 매 실행 전 `DELETE FROM reservations` 실행 |

`201 Created`는 예약 성공, `409 Conflict`는 중복 예약 차단으로 정의했다. 따라서 이 시나리오에서 기대 결과는 성공 1건, 충돌 99건, 예상 밖 오류 0건이다.

```text
100개의 동시 요청
→ 성공 1건
→ 충돌 99건
→ DB 예약 행 1건
```

## 3. 비교한 구현

### 비관적 락

스터디룸 행을 `PESSIMISTIC_WRITE`로 먼저 잠근 뒤, 중복 예약을 검사하고 저장한다. 뒤따른 요청은 앞선 트랜잭션이 끝날 때까지 대기한 후 중복 여부를 다시 확인한다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<StudyRoom> findForUpdateByIdAndActiveTrue(Long id);
```

### 낙관적 락

스터디룸의 `@Version` 필드와 `OPTIMISTIC_FORCE_INCREMENT`를 사용한다. 요청은 먼저 진행되며, 커밋 시점에 버전이 달라졌다면 먼저 커밋한 요청만 성공하고 나머지는 충돌한다.

```java
@Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)
Optional<StudyRoom> findForOptimisticLockByIdAndActiveTrue(Long id);
```

낙관적 락 충돌은 `ObjectOptimisticLockingFailureException`으로 처리하고 API에는 `409 Conflict`로 응답한다.

## 4. k6 스크립트

테스트 스크립트는 [`tests/k6/reservation-lock.js`](../../tests/k6/reservation-lock.js)에 있다.

```javascript
reservation_race: {
  executor: 'shared-iterations',
  vus: 100,
  iterations: 100,
}
```

스크립트는 실행일 기준 다음 날 10:00~11:00로 예약 시간을 자동 생성한다. `201`과 `409`는 예상 응답으로 처리하고, 다른 상태 코드는 `unexpected_error`로 집계한다.

## 5. 정확성 결과

두 방식 모두 3회 실행에서 같은 결과를 냈다.

| 방식 | 성공(201) | 충돌(409) | 예상 밖 오류 |
| --- | ---: | ---: | ---: |
| 비관적 락 | 1 | 99 | 0 |
| 낙관적 락 | 1 | 99 | 0 |

두 방식 모두 같은 시간대의 중복 예약을 하나만 저장하도록 동작했다.

## 8. 해석과 선택 기준

두 방식 모두 중복 예약을 막는 정확성 조건은 만족했다.

비관적 락은 DB 행을 먼저 잠가 충돌 처리가 직관적이고, 대기 후 중복 예약 여부를 확인할 수 있다. 반면 모든 경쟁 요청이 같은 행 잠금을 기다리므로 경합이 많을수록 대기 시간이 생긴다.

낙관적 락은 행을 먼저 잠그지 않아 이번 높은 경합 조건에서 더 낮은 응답 시간과 높은 처리량을 보였다. 다만 충돌한 요청은 버전 검증 시점에 실패하므로, 서비스는 `409 Conflict`를 사용자에게 명확하게 전달해야 한다.

이 결과는 로컬 환경에서 수행한 상대 비교 결과다. 실제 배포 환경의 절대 성능은 서버 사양, DB 연결 수, 네트워크, 트래픽 패턴에 따라 달라질 수 있다. 운영 환경에서는 애플리케이션 락과 별도로 PostgreSQL 배타 제약조건을 유지해 DB 수준에서도 중복 예약 저장을 차단한다.

## 9. 재현 방법

테스트 DB의 예약을 비운다.

```sql
DELETE FROM reservations;
```

대상 락 전략 브랜치에서 테스트 프로필 서버를 실행한다.

```bash
SPRING_PROFILES_ACTIVE=test ./gradlew bootRun
```

다른 터미널에서 k6를 실행하고 JSON 요약을 저장한다.

```bash
k6 run \
  --summary-export docs/performance/results/<strategy>-lock-100vu-<run>.json \
  tests/k6/reservation-lock.js
```
